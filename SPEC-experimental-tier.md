# Spec: `experimental-tier` — PARADE in V1, rest deferred to V2

Status: **partially in V1 — PARADE only**, as an opt-in engine that is never on the default path. Everything else in this spec is deferred to V2 and requires an explicit re-approval at V2 kickoff.
Parent: `CAPABILITY-MAP.md`

## Why this spec exists before implementation

This module is kept off V1's default path so that V1's public claim — "an orchestrator over proven tools, no new algorithms" — stays true. PARADE is the single exception, added because it is the only available 3′UTR engine and because MIT licensing and an installable Python package make the exception defensible. It ships with the full reliability contract below already binding; the contract is not something V1 can postpone, because a research-grade model in the same notebook as LinearDesign must be labelled and isolated from the moment it is selectable.

The remaining risk this spec addresses is not scheduling: it is that research-grade generative and predictive models get presented with the same authority as LinearDesign or ViennaRNA. The reliability contract below is settled now so that (a) V1 never has to retrofit it, and (b) the V2 work cannot quietly lower the bar.

## Objective

Give users who opt in access to generative UTR models (V1: PARADE; V2: UTRGAN, Smart5UTR) and epitope/antigen prediction (V2), honestly labelled, reproducibility-tested, and structurally incapable of contaminating the proven-tool path.

## Reliability contract (binding on any V2 implementation)

- **XT-1.1 Opt-in is per workflow, not global.** A user enables the tier for a run with an explicit action that states what it is and is not. Default is off in every configuration path, including headless runs. No persisted profile may pre-enable it. **This applies to V1's PARADE as strictly as to anything added later: PARADE must never appear in `default_adapters`, in a fallback chain (RD-2.11), in a saved profile, or in a preset config file.** A run that reaches an experimental engine without a user action in that run is a defect, not a convenience.
- **XT-1.2 No experimental output may enter the proven-tool path by default.** Using an experimental UTR in a construct requires an explicit confirmation, and every downstream artifact is flagged `experimental_derived` (filename metadata, summary, order CSV notes, report banner).
- **XT-1.3 Experimental results never affect any pass/fail criterion or overall run status.** They render in their own report section (already reserved by `SPEC-rna-qc-additions.md` QC-7.2) and are excluded from `qc_summary.csv` status columns.
- **XT-1.4 Hard labelling.** Every experimental output carries: the `experimental` marker, the model name and pinned version, its citation, the upstream paper's stated scope/limitations, and a fixed sentence that the output has no wet-lab or clinical validation. Labelling is generated by the framework, not left to each adapter.
- **XT-1.5 Reproducibility gate.** Each experimental adapter must either (a) reproduce a recorded reference output exactly under a fixed seed on the declared runtime, or (b) reproduce it within a documented tolerance with the reason stated (e.g. GPU nondeterminism). Tolerance-based agreement is acceptable; the tolerance value and its justification must be written down, not chosen to make a test pass. A snapshot must exist before the adapter is registered. The test guards reproducibility, **not** biological quality — the spec must not let a passing test be read as evidence the model works.
- **XT-1.6 Weights integrity.** Model weights are pinned by hash with checksum verification at load; the licence permitting local inference is recorded; if weights cannot be redistributed, the adapter documents the fetch path and fails with an actionable message when unavailable. Never a silent fallback to a different checkpoint.
- **XT-1.7 Availability is honest.** Missing GPU, missing weights, or an unreachable dependency produces `not_run` with the reason. The tier's absence never downgrades a proven-tool result and never becomes a `pass`.
- **XT-1.8 Caveats are documentation, not vibes.** `docs/experimental-caveats.md` holds, per model: what it was trained on, what it predicts, known failure modes, and the conditions under which its output should be ignored. It is cited from the report.
- **XT-1.9 Runtime budget.** Each adapter declares expected runtime and aborts on ceiling, like the proven adapters, so an opt-in cannot strand a session.
- **XT-1.10 Single notebook, per-engine toggle.** All experimental engines live in the same notebook as the proven workflow, each behind its own toggle. An engine that is toggled on but unavailable reports `not_run` with the reason; the toggle state and the resolved engine list are recorded in the manifest.

## Engine candidates and Colab viability

Availability is not a binary, so every experimental engine is presented with one of three maturity labels in the UI and the report. All three appear as selectable options; only the first carries a reliability claim.

| Label | Meaning |
|---|---|
| `supported` | Installs on the pinned Colab runtime, weights hash-pinned, snapshot test in CI |
| `best_effort` | Appears in the UI and may run, but the environment is fragile or the weights are unpinned; no reliability claim, labelled as such |
| `unavailable` | Documented with a concrete reason (licence, framework age, server dependency); shown so the user knows the option exists |

Candidates, with the release they are planned for, and the verdict that must be confirmed by a short spike before any is promised:

| Engine | Release | Role | Expected Colab fit | Licence | Proposed label |
|---|---|---|---|---|---|
| **PARADE** | **V1 (opt-in)** | 5′ **and** 3′UTR generation (diffusion, genetic algorithm) plus prediction (activity, stability) | Medium: conda-only `environment.yml`, GPU recommended for generation, ~4 GiB RAM for prediction alone | MIT (confirmed in repo) | `best_effort` for V1; `supported` after a pip-repin spike |
| Smart5UTR | V2 | 5′UTR generation (transformer) | Medium–high (PyTorch-era) — checkpoint availability is the open question | Verify | `supported` if weights can be fetched and hashed |
| UTRGAN | V2 | 5′UTR generation (GAN) | Low–medium — TF1-era code is the main risk on a current runtime | Verify | `best_effort` unless a maintained fork exists |
| MHCflurry | V2 | MHC class I (and class II in its 2.x line) binding prediction | High — pip-installable, CPU/GPU, no registration | Open source (verify exact terms) | `supported`, recommended primary |
| NetMHCpan / NetMHCIIpan | V2 | MHC binding | Only with a licence-gated download | Academic, not redistributable | `unavailable` unless user-supplied locally |
| IEDB API | V2 | MHC binding via web service | Depends on a remote service and its rate limits | Terms of use | Optional fallback, never the default path |

Two further engines were added to the *main* workflow by decision (2026-11-16), because they are proven and permissively licensed:

- **DNAChisel** (constraint-based sequence design, MIT) — now the sanctioned route for CpG/UpA depletion, forbidden-motif avoidance, and restriction-site removal: it applies constraints rather than new algorithms, so it satisfies the project's core rule without a recoder (`rd-2.8`, `qc-3.3`).
- **LinearFold** (fast structure prediction) — now a second structure-metrics engine alongside ViennaRNA (`rd-2.9`). LinearDesign already uses linear-time folding internally, so the results are broadly comparable, but values must stay engine-attributed.

PARADE covers 3′UTRs, which V1 otherwise takes from the reference library. It is therefore the most valuable engine in this tier — and the one with the thinnest maintenance base (three commits, a single group, weights on Zenodo, preprint not yet peer-reviewed). That combination is exactly why it ships opt-in rather than as a default: reference UTRs remain the V1 default precisely because they cannot rot, and PARADE is offered to users who want a generated UTR and accept the label that comes with it.

## Requirements

### V1 scope — PARADE only

- **XT-1.11** In V1 exactly one adapter from this tier is registered: `parade`. It is listed with maturity `best_effort` (RD-2.10), it is never in a default set, and every run that uses it is labelled `experimental_derived` end to end. The rest of this section describes V2 work and is recorded here so the contract is not renegotiated later.
- **XT-1.12** The three maturity labels are user-visible in V1 even with one engine registered, because the label is what tells the user why PARADE's output differs in status from LinearDesign's. A label shown only once a second engine exists is a label that never gets built.

### Generative UTR models

- **XT-2.1** Adapters: V1 ships `parade`; V2 adds `utrgan` and `smart5utr`. Each returns a UTR `DesignResult`-compatible record, so QC and construct code consume it unchanged. PARADE is the only one of the three that produces 3′UTR candidates and UTR activity/stability predictions; UTRGAN and Smart5UTR are 5′UTR generators.
- **XT-2.2** Generation count and diversity: the user requests N candidates (bounded); each candidate keeps its model-assigned score/rank *and* the upstream score's meaning, without re-normalising it here.
- **XT-2.3** No automatic winner. Selection is the user's, consistent with RD-4.1.
- **XT-2.4** PARADE (`autosome-ru/parade`, MIT) is verified as both predictive and generative, for both 5′ and 3′UTRs, and installable rather than server-only. It ships in **V1** under the plugin contract in two roles: generation (diffusion or genetic algorithm) and prediction (activity, stability). Its conda-only `environment.yml` is the main Colab risk, so the adapter must be re-pinned to pip wheels before it can be labelled `supported`; until then it is `best_effort`. The V1 acceptance bar is narrower than `supported`: install and produce one UTR on the pinned runtime, with the result labelled. If the repin fails, PARADE remains registered as `unavailable` with the reason rather than being removed — the user should still learn the option exists (RD-6.6).
- **XT-2.6** PARADE's predictive models may also be offered as an experimental QC engine (UTR activity/stability). If used that way the results stay in the experimental report section and cannot change run status (XT-1.3): a learned activity score is a model output, not a measurement.
- **XT-2.5** Generated UTRs are validated structurally (nucleotide alphabet, length bounds, no accidental start codon where that would be wrong) before being offered downstream — a structural check is not a biological claim.

### Epitope / antigen prediction

- **XT-3.1** Predictions come only from an existing predictor. **Recommended primary: MHCflurry** — pip-installable, no registration, open licence, and it covers class I with class II in its 2.x line. NetMHCpan and NetMHCIIpan are excluded from the default path because their licence forbids redistribution and requires registration; a user-supplied local install may be supported as `best_effort`. The chosen tool, its version, allele set, and licence are recorded in the manifest and in every output.
- **XT-3.2** Report scope explicitly: which MHC classes, which HLA alleles, predicted vs. eluted-ligand-trained backend, and what the score means. Population coverage claims are out of scope unless computed by an upstream tool that states its method.
- **XT-3.3** Output is a ranked table with provenance and a clear statement that binding prediction is not immunogenicity, and that no in-vivo response is predicted.
- **XT-3.4** Interface constraint: an epitope-derived polyepitope construct must flow through the `rna-design` request contract (`DesignRequest` → designs → `dna-construct`). The tier must never write into `dna-construct` internals — this is the one place in the map where a cycle could appear.
- **XT-3.5** Linker/spacer design for polyepitope constructs is **not** in scope for this tier's first version unless an upstream tool provides it; otherwise it becomes its own delta spec.

## Tech Stack (V1: PARADE; V2 additions to be confirmed at V2 kickoff)

Python 3.11 + PyTorch, pinned model checkpoints with hash verification, the existing `mrna_design` contracts and QC layer. No new training, no fine-tuning, no in-house model code. V1 pins PARADE only; UTRGAN and Smart5UTR are V2 and bring their own framework pins.

## Testing Strategy

- Reproducibility/snapshot per adapter (XT-1.5), on the declared runtime, with seed documented.
- Opt-in gate tests: default-off in notebook, headless, and any config path; `experimental_derived` flag propagates to construct and order block.
- Isolation tests: experimental results cannot change `qc_summary.csv` status columns or run status; report section presence and emptiness when disabled.
- Label/citation tests: every experimental artifact carries the marker and citation; a missing citation fails rendering.
- Failure tests: missing GPU/weights → `not_run` with reason, never a silent fallback.
- No test asserts biological validity. Any such assertion would be a category error and must be rejected in review.

## Boundaries

- **Always:** label, cite, flag downstream artifacts, verify weight hashes, keep the tier out of pass/fail, document limitations.
- **Ask first:** enabling the tier by default anywhere; adding a model; changing snapshot tolerances; promoting an experimental output into the default construct path; any claim about immunogenicity or expression.
- **Never:** present an experimental result as equivalent to a proven-tool result; let a `not_run` read as `pass`; re-normalise or reinterpret upstream scores; train or fine-tune a model in this repo; make an experimental dependency mandatory for the proven path.

## Success Criteria (V1 subset first, then the eventual V2 build)

| XT-SC7 | **V1:** PARADE installs and produces one UTR on the pinned Colab runtime, or reports `unavailable` with a concrete reason; either outcome is recorded in `docs/experimental-caveats.md` | One-session spike, result committed as an ADR |

## Out of Scope (Deferred)

- Model training, fine-tuning, or architecture changes — the no-new-algorithms constraint applies here too.
- De-novo protein/antigen design — adjacent field, separate project.
- Immunogenicity, expression-yield, or stability prediction as validated numbers — no admission of a claim we cannot test.
- Multi-allele population-coverage optimisation — needs its own method and citation.
- Any experimental tool that cannot be installed reproducibly in Colab — availability is a prerequisite, not a V2 stretch goal.

## Open Questions

1. **PARADE's pip repin (V1 blocker).** The conda-only `environment.yml` is the one thing standing between `best_effort` and `supported`. If it cannot be repinned, PARADE ships as `unavailable` — still listed, still labelled — and V1's 3′UTR story is the reference library alone.
2. **PARADE sustainability:** three commits, one author group, weights on Zenodo, preprint not yet peer-reviewed. What is the fallback if it stalls — keep the reference UTR library as the permanent default, or vendor a snapshot?
3. **Optimus 5-Prime vs PARADE for 5′UTRs:** if Optimus does not fit the Colab free tier (RD Open Question 2), the reference library becomes the default 5′UTR source and PARADE is the opt-in generative alternative. Confirm that reading before planning, because it decides whether PARADE needs the 5′UTR role in V1 or only the 3′UTR role.
4. **Tolerance definitions:** for generative models, what agreement is meaningful — identical ranking of top-k candidates, a score within ε, or a distributional check? Bit-identity will not survive GPU runs, and a tolerance chosen after seeing the failure is not a gate.
5. **Epitope scope (V2):** class I only, or class I + II? MHCflurry 2.x covers both; the allele set and the reporting depth follow from this.
6. **Reviewer stance:** will the paper's reviewers accept the `supported` / `best_effort` / `unavailable` labelling as a distinction from "we ship new methods"? This wording is the release claim, and it was deferred for later discussion.
